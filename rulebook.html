📖 Feature-map rulebook

Stage 2 of the pipeline: sliced idea → smallest features + user-side verification. The binding rules, in plain English.
updated 2026-08-31 · mirrors AGENTS.md in the repo

The flow — every idea, every time

Input in, three artifacts out — same turn, before any code exists.An idea-slicer link — or injected source documents (a PRD, a plan, an SDD, or both a PRD and an SDD) — produces, together: the feature inventory (maps/<slug>.md), the tester kit (verify-<slug>/ — the driving manual + 25-style recipe files), and the rendered page (via node render.js, never hand-edited).
The connection.A feature map born from an idea-slicer map tracks it. A thought sliced into the idea updates the feature map, the page, and the kit's recipes in the same turn — new or changed features only; stable features untouched.
Pre-build honesty.The kit exists before anything is built. Harness lines only real code can answer are marked PRE-BUILD — the kit is a draft until its first executed proof run. When an app repo exists: copy the kit in, ground it, prove it end to end once. An ungrounded kit is never reported as proven.

The page — structure and identity

Its own visual identity.Never the idea-slicer look: engineering-blueprint theme — grid paper, monospace labels, blue feature boxes, teal verification boxes. No purple, no pill cards.
Detail is the product.Every aspect written out in full — numbered build steps, behaviour bullets, lifecycle as a trigger→steps→end chain. One-line summaries fail the page.
Two linked boxes per feature.Feature box (steps + sub-feature chips + behaviour + lifecycle), a teal "verified by" connector, then the verification box below. The connector makes the pairing obvious.
The verification box carries the merged P-Stack recipe.How to get to it (user POV) · preconditions · labeled driving steps (action → observable result) · gotchas (amber) · success/failure parameters. One unified page — no separate kit page; the raw kit is footer-linked for the tester agent.
Counts up top.The header stats bar always states how many features and sub-features were found, plus verification recipes.

The rules

1. Smallest useful feature.As small as possible without stopping being a feature — it must do one observable thing for a user or another feature. If splitting removes anything observable, stop.
2. Anti-over-split.Two portions that can never be triggered, failed, or verified independently are one feature.
3. Three aspects per feature, always.The feature (what it is + smallest build steps) · the behaviour (states, what can happen to it, variants) · the lifecycle (every trigger point → progression → every end state).
4. Verification from the user's endpoint, performed by the tester agent.Steps start at the user surface ("can the button be clicked?") and end at visible proof on a system the user can see (the exchange's open-orders list). The tester agent performs every step — never Bobby — inside a ProofShot recording; Bobby witnesses the video. Never backend tests, never a reported "done".
5. Success and failure parameters, always.Success = visible proof it works. Failure = the observable gap that proves it does not (click registers, nothing reaches the exchange).
6. No user-visible checkpoint? Flag it, don't skip it.Name the surface where proof would appear and mark it as needing a user-endpoint view.
7. Mobile is the primary screen.No visual change is done until verified at ~390px as well as desktop.
8. Contradictions stop the line.If the source idea map conflicts (thresholds, better/worse directions), quote both sides and ask Bobby — never map over a conflict.
9. Terse chat, rich page.Plain everyday English; technical terms glossed in a few plain words on first use.

Publish rhythm

Straight to main.Bobby's standing instruction (same as idea-slicer and ELI5links). The site updates ~1 min after push — verify with a curl grep on the live URL, never just a clean commit.
